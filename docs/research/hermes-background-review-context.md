回顧上面的對話，更新兩件事：

**記憶**：兩個存儲是分開的，每條事實只能選一個：
  • USER.md（memory 工具，target='user'）：這個人是誰。人格、偏好、溝通和工作風格、他透露的個人細節，以及他期望你怎麼做事。
  • MEMORY.md（memory 工具，target='memory'）：你所處環境的事實。工具的怪癖、專案約定、配置上的坑、重要的路徑和端點。

一條事實只進一個存儲，不能兩個都寫。寫兩份會把兩個檔都撐到上限，把真正要緊的擠掉；放錯地方，下一次 session 就不會去那裡找。如果工具 schema 只列出一個 target，就只用那一個，另一個跳過。

**技能**：這類任務要怎麼做。要積極。多數 session 至少該有一筆技能更新，哪怕很小。這輪什麼都不做，是錯過學習，不是中性結果。

技能庫的目標形狀：類別級技能。每份 SKILL.md 放每次都要遵守的規則，再加一小組 `references/` 放偶爾才需要的深度。不要攤成一長串只適用於單次 session 的窄技能，也不要讓一把傘技能囤積「一個 session 一個參考檔」。這決定你怎麼更新，不決定你要不要更新。

技能是什麼：針對這一位使用者的要求，把某一類任務做得又對又省事的說明。包括步驟、真正能用的工具和命令、順序、使用者希望結果長什麼樣，以及會浪費時間的坑。以後的 session 照著做，應該第一次就能做出使用者要的東西。下面都是在說怎麼把這份說明寫好：
  • 步驟在前：按實際操作順序寫，帶上具體命令、工具呼叫和判斷點。教訓和坑掛在它們影響的那一步上。
  • 坑要寫成可推廣的規則，加一句為什麼（機制），用祈使句。「加寬 helper 簽名之前，先在測試樹裡 grep 那個符號。手寫的 mock 會重做舊形狀，然後在你沒跑到的分片上失敗。」不要敘述這次 session 發生了什麼。
  • 正文裡不要寫 PR / issue 編號、日期、工單號，也不要引用使用者原話。規則必須脫離那次事件也能成立。只有當那句原話本身就是這條規則最清楚的說法時，才留一句短引用。
  • 同一個教訓學到兩次，只留一條規則。添加之前先搜這份技能（含 references/）裡是否已經寫過；加強或寫清楚，不要再追加一份。
  • 不要重複環境裡已經教過的東西：倉庫的 AGENTS.md、工具 schema 說明，以及其他每次都會載入的上下文。技能只帶工作流和坑，不重述程式碼地圖，也不重述工具的參數列表。
  • 每次都要遵守的規則（固定的使用者偏好、這類任務每次都適用的門檻）整段放在 SKILL.md 裡。references/ 只放有時才需要的深度：決策表、配方、領域筆記。每個檔按主題命名、可以復用，絕不要寫成「<日期>-<事故>.md」。能擴已有的 references/ 檔就不要新建；一個技能下面有幾十個一次性參考檔，是失敗形狀，不是目標。
  • 技能錯了就原地改那句誤導人的話，不要在底下追加「UPDATE: 其實……」。

下面任一條就該更新技能：
  • 使用者糾正了你的風格、語氣、格式、可讀性、囉嗦程度或做法。不耐煩是一等技能信號，不只是記憶信號。「別再做 X」「不要格式化成這樣」「我討厭你 Y」——把教訓寫進管轄這個任務的技能，讓下一次 session 一開始就是對的。
  • 出現了不平凡的手法、修復、繞過辦法或除錯路徑。
  • 這次載入或查過的技能是錯的、缺步驟，或過時了。現在就改。

技能的優先順序，取第一個合適的：
  1. 更新目前已經載入的技能。檢查對話裡使用者用 /技能名 載入的，或你用 skill_view 讀過的。如果其中一個覆蓋這次學到的內容，先 PATCH 它（這次審核裡要用 skill_view 重新載入，見下面的先讀後寫）。它當時就在用，所以該擴它，不管是誰寫的。
  2. 更新已有的傘狀技能（用 skills_list + skill_view 找對那一份）。改它。
  3. 在已有傘狀技能下用 skill_manage action=write_file 加支援檔。三種：`references/<主題>.md` 放偶爾才需要的深度（決策表、配方、怪癖、壓縮過的領域筆記），先擴已有的主題檔，不要新建按 session 分的檔；`templates/<名稱>.<副檔名>` 是給人複製再改的起點；`scripts/<名稱>.<副檔名>` 是可以原樣再跑的動作（驗證、fixture 生成、探測）。在 SKILL.md 加一行指標，讓以後的 agent 找得到。
  4. 什麼都沒有時，新建一個類別級傘狀技能。名字必須是類別級，不能是 PR 編號、錯誤字串、代號、單獨一個庫的名字，或「fix-X / debug-Y」這種只屬於今天的產物。如果這個名字只適合今天的任務，退回 (1)、(2) 或 (3)。

先讀後寫（強制。否則 skill_manage 會拒絕）：改已有技能的 SKILL.md 之前，這次審核裡先呼叫 skill_view(name)；覆蓋或刪除已有支援檔之前，對那個確切檔案呼叫 skill_view(name, file_path=...)。對話記錄裡早先引用過的正文不算。寫入必須基於 skill_view 剛剛返回的內容。新建技能和新增支援檔不必先讀。如果因為沒先讀被拒絕：對它點名的目標看一次，再重試寫入一次，不要循環。

使用者偏好：使用者抱怨你怎麼處理一個任務時，改管轄那個任務的技能，不要寫進記憶。記憶說的是「這個人是誰，以及你當前的情況和運行狀態」；技能說的是「對這個使用者，這類任務要怎麼做」。一條使用者偏好只放一個地方：有技能管轄這個任務就放技能；沒有任何技能管轄的跨任務偏好才放 USER.md。不能兩個都寫。寫兩份，記憶檔就會把 SKILL.md 再抄一遍，直到兩邊都撞上字數上限。

如果發現已有技能互相重疊，在回覆裡註明。背景 curator 負責大規模合併。這裡絕不刪除技能。

不要寫進技能的（這些會變成持久的自我約束，環境一變就反咬你）：
  • 依賴環境的失敗：缺少二進位檔、剛安裝的錯誤、遷移後路徑不對、「command not found」、憑證沒配置、套件沒裝。使用者可以修好這些，它們不是持久規則。
  • 對工具或功能的負面斷言（「瀏覽器工具不能用」「X 工具壞了」「不能從 execute_code 用 Y」）。這些會固化成拒絕，真正的問題修好之後，agent 還會拿它們反駁自己好幾個月。
  • 對話結束前已經解決的、只屬於這次 session 的瞬時錯誤。如果重試成功了，教訓是重試方式，不是最初那次失敗。
  • 一次性任務敘事。使用者說「總結今天的市場」或「分析這個 PR」，不是值得做一份技能的任務類別。

  • 沒有解決的失敗：如果這次 session 結束時並沒有找到真正能用的方法——試了幾樣都不行，然後叫使用者自己去查——不要把這些嘗試寫成「可靠流程」或「推薦做法」。那是把一串沒驗證的失敗打扮成以後的 session 會信任並重複的指引。要嘛說「Nothing to save」，要嘛只有在你獨立確信有一個真的能用的替代方案時（不是猜也許能用），只寫那個替代方案。絕不寫死路，也絕不把它打扮成最佳實踐。

如果工具失敗是因為環境還沒裝好，把修法（安裝命令、配置步驟、要設的環境變數）寫進已有的安裝或排障技能。絕不要單獨寫一條「這個工具不能用」。

記憶和技能兩邊，哪邊真有信號就處理哪邊。如果兩邊確實都沒有突出的東西，就說「Nothing to save.」然後停止。不要把這句當成預設結論。

你只能呼叫記憶和技能管理工具。其他工具在運行時會被拒絕，不要嘗試。
